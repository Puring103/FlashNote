# 核心架构与同步设计

同步与存储核查基线为 `58592f0`，密钥策略更新于 2026-11-26。目标是让同一人的多台设备能离线编辑，并在重新联网后保留独立修改。共享 Rust 核心、单机 SQLite、按对象比较版本以及可见的冲突副本都适合这个目标。优先需要补强的是服务端回档识别、上传失败时的拉取，以及跨对象的分组归属。实测场景和验收条件见[本次审查](架构审查-2026-11-25.md)。

## 一张便签如何表示

`Note.id` 跨修改保持稳定，`revision` 随保存变化。单个 `group_id` 指向平级分组。全零 UUID 标识默认分组。分组有名称、颜色、图标、顺序和删除标志。标题、链接列表、创建与修改时间、回收时间以及冲突关联都属于便签负载。

`blocks` 保存有序正文，支持 Markdown、图片、远程图片、音频和普通文件。块 ID 表示正文中的一个节点，asset ID 指向附件字节。音频块还保存时长、转写状态和文字。编辑器将媒体映射为带块 ID 与缩进深度的占位链接，保存时恢复结构；正文可重排而无需重写附件。语义比较会忽略 Markdown 块的 ID 变化。

从正文移走的媒体可以留在 `media_archive` 供撤销恢复。`blocks` 和归档中的附件都会参与同步、ZIP 导出和引用保留。用户删除一张内嵌图片后，其他设备仍可能下载其原件。要改变这项取舍，需要一并定义跨设备撤销、导出内容和空间回收的行为。

## 本地资料库与导出

| 位置 | 写入内容与用途 |
| --- | --- |
| `notes.sqlite3` · `objects` | 当前 note、group 和本机 settings 的 JSON。资料库格式 v3 使用 WAL，打开时加载当前对象并建立内存列表。目录锁限制同一目录的并行打开。 |
| `revisions`、`outbox` | 完整修订快照、父版本、设备和本地时间，以及修订的确认状态。保存业务对象时同事务写入。历史可按保留期手动清理。 |
| `sync_heads`、`sync_packets`、`sync_state` | 每对象最后已知云端版本及其内容、待重试的原始加密信封、增量游标等状态。待传对象通过当前版本和基线的差异选出，一张便签的多次离线保存通常只上传最新内容。 |
| `assets/`、`sync-assets/`、`cache/open/` | 附件原件、可重试的同步密文、交给外部程序打开的明文副本。文件写入与 SQLite 事务有各自的提交边界。 |
| `device-id`、`sync-owner.json`、受平台保护的密钥与会话文件 | 标识本机设备和资料库归属。首次绑定账户后，退出会清除本地会话，保留数据与绑定关系。其他账户使用独立资料目录。 |

移入回收站写入 `deleted_at`。永久删除清空当前内容，清理该对象本机旧修订，并保留空的删除版本供离线设备接收。旧同步基线在确认前仍可能持有正文，其他设备另有自己的历史。附件清理检查当前内容、保留历史和基线。可移植 ZIP 收录清单和附件原件，不带口令，账户凭据、同步基线和本机历史均不随包迁移。[归档实现](../crates/flashnote-core/src/archive.rs)

## 一轮同步如何完成

1. **准备。** 客户端读取账号、游标及有变化的 note/group，取最后云端修订作为 `base_revision`，按当前对象生成或复用信封。尚有未完成附件占位的便签等待后续处理。桌面当前一次准备所有待传对象。
2. **上传。** 先确认每个引用附件已存在，缺失时上传，再 PUT 对象。服务端在 SQLite 写事务中校验基线和附件引用，更新配额、当前对象与引用。相同修订和摘要可凭回执重试；基线过期返回含当前信封的 409，客户端保留修改、转入拉取。其他上传错误会中断本轮。
3. **拉取。** `GET changes?after=…` 按服务端序号递增，每页最多 16 个当前对象。服务端覆盖旧对象，同一对象的中间修订可以被跳过。客户端验证信封、解密并准备附件，再将本页交回 Store。浏览接口 `GET objects` 拥有独立分页协议。[浏览协议](网页版接入策略.md)
4. **提交。** 客户端校验登录代次及起始游标。上传确认、本页对象、修订、合并结果、同步基线与新游标在一个 SQLite 事务提交。网络期间的新编辑保留为待传。下载的附件可能先于事务写盘。后续页独立提交。
5. **继续收敛。** 桌面通过后台传输和后续轮次提交新合并版本。Android 手动同步和同步 CLI 调用 `once`，它会取完后续拉取页；本轮合并产生的待传版本要到下次上传才能出现在第三台设备。

### 两端都改了同一对象

共享基线、本地当前版本和云端当前版本构成三方输入。标题、归属等字段用三方选择，正文对编辑器 Markdown 做按行合并，媒体按块 ID 对齐。互不冲突的修改生成新修订。遇到无法合并的便签，原 ID 安装云端内容，本地内容作为关联副本保存，副本 ID 由对象及双方版本确定，支持重试和人工选择。分组按字段合并，普通分组冲突可生成离线副本，默认分组单独处理。不同对象之间的引用需要额外维护，尤其是分组删除与离线新建的组合。

### 服务端保存什么

`vaults` 以 issuer 和 subject 唯一确定资料库，记录用量和配额。`client_keys` 保存端到端库的密钥指纹，`managed_keys` 只为托管库保存封装后的账户密钥。`objects` 保存每个对象的最新信封及序号，`receipts` 保存不可变修订摘要和序号以确认重试，`assets` 保存附件密文，`refs` 记录当前对象的附件引用。服务端能列出最新对象，历史浏览依赖各设备本机保留的修订。附件上传请求体上限 64 MiB，对象 JSON 信封请求体上限 8 MiB，包含 Base64 开销。无引用附件经过一天宽限期后可回收。[服务端实现](../sync-server/server.py)

## 加密与信任边界

| 边界 | 当前实现 | 对使用者的含义 |
| --- | --- | --- |
| 设备存储 | 本机 SQLite 的当前正文、历史、基线及附件原件为明文。Windows 用 DPAPI，Android 用 Android Keystore，Linux 通过 Secret Service 保护密钥或包装密钥。 | 有权读取资料目录者可直接读取内容。丢失设备时，静态保密依赖系统账户、设备沙箱和磁盘保护。 |
| 客户端到同步服务 | 非回环地址要求 HTTPS。对象和附件另用 32 字节资料库密钥做 XChaCha20-Poly1305 加密，每次新加密生成随机 24 字节 nonce。对象认证数据绑定完整信封头，附件绑定协议上下文和附件 ID。 | 密文验真后才应用。服务端可见库、对象、设备、修订与基线 ID、类型、附件关系、大小和访问时序。 |
| 默认端到端模式 | 本机生成 128 位随机熵，BIP39 英文词表编码为 12 词。HKDF-SHA256 以库 UUID 文本为盐、以 `flashnote/e2ee/v1/key` 为 info 派生 32 字节密钥。服务端对密钥材料仅保存带上下文的 SHA-256 密钥指纹；创建时原子确认首个指纹。 | 登录、服务端备份或重置密码均不足以解密。已授权设备受平台保护地保存恢复材料，其他设备需输入原词。 |
| 可选托管模式 | 服务使用主密钥和 AES-GCM 封装账户密钥，经身份校验后通过 HTTPS 向客户端发放。 | 服务管理员具备解密能力。切换新库默认策略不会转换旧库。 |
| 备份和恢复 | 客户端 ZIP 含明文业务数据。服务器完整备份同时包含身份服务状态、密钥和数据。 | 两种备份均需单独保护。服务端恢复还要验收已同步过的旧设备。 |
