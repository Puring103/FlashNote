# 核心架构审查 · 2026-11-25

审查基线为 `58592f0`。对于个人离线便签，共享领域模型、本地事务、按对象同步与服务端条件写入值得保留。以下三项均在 Windows 本机、临时资料库和真实 HTTP 同步服务上观察到。测试身份使用项目自带的 Casdoor 替身。

## P1 · 服务端回档后旧设备静默漏收

**观察。** 两端同步后备份服务器数据库，再新增三张便签并让两端同步。把服务端数据库恢复至备份，用第三台空白设备同步并新增便签。原设备再次同步成功，待传数为零，却没有收到第三台设备的新便签。

**原因。** 游标只有数值。回档后序号可以重用；旧设备以较高游标请求时，服务端查不到更高序号就原样返回该游标。设备上已确认的对象同时保留旧基线，也不会主动补传。即使新写入后来超过旧游标，期间被跳过且未再修改的对象仍会遗漏。[服务端 changes](../sync-server/server.py) · [客户端 read_cursor、prepare_cycle、apply](../crates/flashnote-core/src/sync.rs)

**修订方向与验收。** 让游标绑定服务端数据世代，恢复流程显式更换世代。旧客户端检测变化后需重新核对双方对象与待传内容，并对仅本机持有的修订提供保留路径。仅把游标归零不能恢复云端已经丢失的对象。验收应同时覆盖旧设备、新设备、备份后的已确认编辑和尚未上传的编辑。

## P1 · 单个上传失败阻塞整轮拉取

**观察。** A 上传一张新便签后，将临时库的配额设为当前用量。B 有一张待传便签，调用普通同步失败，也没有下载 A 的便签。同一会话单独执行已有的只拉取流程，B 随即收到 A 的便签。

**原因。** `transfer` 先顺序上传再读 changes，配额错误会提前返回，后续对象和本轮拉取都无法执行。已完成的远程写入依靠回执重试，本机尚未拿到本轮确认。持续超配额时，普通重试还会遇到同一障碍。[客户端 transfer](../crates/flashnote-core/src/sync.rs) · [服务端 charge](../sync-server/server.py)

**修订方向与验收。** 将可恢复的对象上传错误与拉取进度分别记录。保留失败修订的待传状态，在账号和完整性校验通过的前提下继续接收远端更新，并让界面分别显示收取结果和具体失败对象。用配额耗尽验证能收不能发；释放空间后原对象应只确认一次。

## P2 · 删除分组与离线新增产生悬空归属

**观察。** 两端已有分组 G。A 删除 G 并指定默认分组为迁移目标，B 离线新增一张归入 G 的便签。双方交替同步三轮后，两端待传数均为零，分组列表均已移除 G，但该便签在两端的 `group_id` 仍是 G。内容保留，按迁移目标筛选会漏掉它。

**原因。** 删除分组的本地事务仅迁移当时已知的便签。分组删除记录只有删除标志，未保留目的分组。远端应用按对象提交，接收新便签时没有对已删除分组重定向。[delete_group](../crates/flashnote-core/src/archive.rs) · [apply](../crates/flashnote-core/src/sync.rs)

**修订方向与验收。** 先定义迟到便签的归属规则。如果应遵从用户选择，删除标记需保存迁移目标，并处理目标再次删除。如果统一回到默认组，应将修正持久化并同步。测试两种到达顺序、跨页到达和第三端首次拉取，检查最终分组可见且各端归属相同。

## 容量与内容保留的取舍

- 桌面打开资料库时装入全部当前对象，上传准备一次持有全部待传对象，拉取才按页提交。大库首次同步的内存峰值和界面停顿需要独立测量，本次没有性能基准。[Store::open](../crates/flashnote-core/src/store.rs) · [prepare_cycle](../crates/flashnote-core/src/sync.rs)
- 本机默认保留完整历史，归档媒体也计入当前引用。历史保留期、归档清理和用户看到的空间统计需要一起解释。云端配额按当前对象密文字节及附件计费，修订回执、Base64、索引和 SQLite 自身占用另计，磁盘需求可能高于界面用量。[本机归档](../crates/flashnote-core/src/archive.rs) · [云端用量](../sync-server/server.py)
