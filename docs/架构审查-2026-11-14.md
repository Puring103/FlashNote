## 修复进展（同日）

已按本报告优先级完成一轮修复：

- 清空已保存便签时，缓存、数据库 payload、修订父链使用同一条删除记录；在该编辑会话继续输入可恢复便签。
- 编辑提交携带实际观察到的 revision 和基础正文。不同位置的修改通过三方合并保留；相同位置冲突会拒绝覆盖并保留窗口中的输入，提示复制另存。此处尚未提供本地窗口冲突的专用比较界面。
- 编辑器核心会明确拒绝组字期间的外部替换；宿主只在接收成功后推进观察版本，并持续重试待接收版本。
- 转写更新覆盖活动/归档音频，忽略缺失或已结束节点；任务代次阻止旧识别结果覆盖新尝试。启动时也恢复归档音频的 Processing 状态。
- 相同文字段重复序列化保留原 ID；同步语义比较忽略文字块 ID，仍保留媒体身份。完全无变化的 Note 保存不再制造修订。
- 图片预览读盘和解码转到后台，最多同时执行两个加载任务。缓存按访问时间逐项淘汰冷项，以 32MiB PNG 字节数为软预算，最近五秒使用的工作集可超出预算；这不是 GPU/解码后内存硬上限。列表虚拟化和持久化缩略图仍属于后续性能工作。

下文问题记录保留为修复背景。完整 EditSession 抽象、应用级统一调度、历史/素材保留策略及数据库访问收口尚未在这一轮整体重构。

修复后验证：`cargo test --workspace --all-targets --quiet` 共 83 项通过（新增 9 项回归测试）；`cargo fmt --all --check` 和 `git diff --check` 通过。真实 Windows IME、多窗口操作和大图库性能仍需交互验收。

## 范围与结论

初次审查按当时工作区进行，包括已有未提交修改，审查阶段没有修改业务实现；后续修复见上方进展。重点为本地存储、同步客户端/服务端、编辑器文档核心及宿主接入。不是对所有平台 API 的逐行安全审计，也没有进行真实 Windows 输入法及多窗口交互验收。

总体方向适合个人本地便签：Rust/GPUI + SQLite + 独立编辑器核心 + 密文同步服务，无需重写或引入微服务。主要问题在状态所有权和更新协议：数据库、Store 缓存、多个编辑器会话、后台任务分别维护状态，跨层更新缺少统一约束。

## 当前框架

| 层 | 实现 | 职责与边界 |
|---|---|---|
| 启动/平台 | `src/main.rs`、`platform.rs` | 数据目录、单实例、迁移补偿、托盘、系统剪贴板 |
| 应用与界面 | `src/ui.rs` | Runtime、窗口、编辑会话、自动保存、后台任务调度、设置、附件呈现；目前职责过多 |
| 领域数据 | `src/model.rs` | Note/Group/Block、搜索、编辑器 Markdown 与持久化块转换 |
| 存储 | `src/store.rs` | SQLite、内存镜像、修订/outbox、附件写入、冲突选择 |
| 本地格式/密码学 | `local.rs`、`crypto.rs` | 旧版迁移、文件替换、附件密文缓存、DPAPI、AEAD、口令派生 |
| 同步客户端 | `src/sync.rs` | 配置/设备加入、prepare→transfer→apply、三方合并、冲突副本 |
| 同步服务 | `sync-server/server.py` | Python 标准库 HTTP + SQLite，鉴权、CAS、密文存储、附件引用、容量、GC |
| 编辑器模型 | `crates/gpui-note-editor/src/document.rs` | Document/Span/Marks、Markdown、事务、选择、历史、输入规则、composition |
| 编辑器视图 | 同 crate 的 `view.rs` | GPUI 布局/绘制、命中测试、输入法、UTF-16 转换、宿主媒体回调 |
| 位置映射 | 同 crate 的 `mapping.rs` | 编辑步骤导致的位置映射 |
| 媒体 | `media.rs`、`remote_images.rs`、`audio.rs` | 文件预处理、远端图片、录音/播放/识别 |

编辑保存链：GPUI 输入 → EditorState → Document → Markdown → Changed → 350ms 延迟 → Note::set_editor_markdown → Store::save_note → objects/revisions/outbox。

同步链：主线程 prepare（差异查询/封包）→ 网络线程 transfer（附件/上传/分页拉取）→ 主线程 apply（合并、数据库事务、游标提交、重载缓存）→ generation 通知各视图。

## 优先修复的问题

### 1. P1：清空已有便签后，数据库和内存版本分叉【已复现】

位置：`src/store.rs:230` 附近的 `save_note` 空内容分支。

已有正文被清空时，数据库写入新 revision 的删除记录；内存却放回原 revision、未删除的 n。数据库 payload 的 parent_revision 也未随 persist 的 parent 参数一起更新，修订表与 payload 可不一致。

后果：后续在内存空稿继续输入时，保存的 parent 来自旧内存版本；同步 apply 重载数据库时，空稿会被同 ID 的删除记录替换。当前保存前检查比较的是内存，所以无法发现这次分叉。

建议：明确“新建空稿”“清空已存便签”“已删除便签”三种状态。若清空意味着删除，内存同步安装同一删除记录；继续输入时明确执行恢复/新建。空稿单独放 DraftSession，避免混入持久化 Note 集合。

复现：创建并保存正文 → 取回最新版 → set_editor_markdown("") → save_note → 比较 Store.notes 与 objects payload。临时测试确认 revision 不同、deleted_at 不同、payload 父版本与写入参数不一致。

### 2. P1：多编辑器保存会绕过乐观并发检查【调用链确认，未做 UI 复现】

位置：`src/ui.rs:664` 的 flush、`:633` 的 current_note，以及 `src/store.rs:217`。

flush 从 Store 取“当前最新版 Note”，再用本视图的整份旧正文覆盖。传给 save_note 的 revision 已经是最新版，因此 store 的 revision 检查必然通过，却无法识别正文基于旧 observed_revision 编辑。

同一便签在中心卡片与独立窗口有各自编辑器时，两个 dirty 会话交错 flush，后保存的全文可以覆盖先保存的修改。只阻止云同步 apply 的 dirty_editors 无法阻止本地会话之间覆盖。

建议：提交内容时携带编辑会话的 base_revision；真正的 CAS 与持久化在同一提交入口完成。不匹配时保留会话内容，执行三方合并或提示冲突。更轻量的方案是同一 Note 共享文档会话、各视图分别保留选区。

### 3. P1：输入法组字时外部更新可能永久跳过【调用链确认，需真实 IME 验收】

位置：`view.rs:230` 的 sync_external、`:675` 附近的 replace_and_mark_text_in_range、`ui.rs:783` 附近的 tick。

组字调用 sync(false)，不会产生 Changed，宿主未必进入 dirty 状态；此时云同步/其他视图可以更新 Store。tick 调用 sync_external，后者因 marked 存在直接 return，但 tick 仍更新 observed_revision。组字结束后，相同外部 revision 不会重试应用。

后续 flush 又从最新 Store 取 Note 并覆盖正文，与问题 2 结合存在丢失外部修改风险。

建议：外部同步返回 Applied/Unchanged/Deferred，只有确认接收后才推进 observed_revision；记录 pending external update。composition 生命周期应纳入编辑会话状态，并在提交时检查 base_revision。

### 4. P2：异步转写未更新移入素材归档的音频【代码确认】

位置：`src/ui.rs:176` 的 Job::Transcript；对照 `:158` 的 Job::Attachment。

用户在识别完成前删掉音频节点，set_editor_markdown 会将媒体放进 media_archive；Attachment 完成会搜索 blocks 和 media_archive，而 Transcript 只搜索 blocks。转写结果因此被忽略，还会保存没有实际变化的便签。撤销恢复素材时，可能保留 Processing 状态而没有结果。启动恢复 Processing 的逻辑也只查 blocks。

建议：统一按媒体 ID 更新当前/归档节点；为任务增加 operation ID，避免同一素材多次重试的旧结果覆盖新结果；节点不存在或没有变化时不要制造 revision。

### 5. P2：文字块 ID 不稳定，却参与同步的语义比较【ID 变化已复现】

位置：`src/model.rs:222` 的 set_editor_markdown，`src/sync.rs:631` 的 semantic。

每次解析回 Note 都为 Markdown 块创建新 UUID，即使 Markdown 内容相同。semantic 仅去掉 revision、parent_revision 和时间，仍保留随机文字块 ID。语义相同的两份正文可能被当成不同内容。

普通三方文本合并有机会消除此差异，但编辑/删除判断使用 semantic，因此这种差异能把本来没有内容变化的另一端识别成编辑，形成不必要的冲突副本。历史和 JSON 也产生无意义变更。

建议：决定文字块 ID 是否具有领域身份。没有则不持久化/不参与语义比较；有则使用稳定匹配或直接持久化结构化文档。增加“相同内容重复设置”“同内容不同文字块 ID 与删除合并”测试。

### 6. P2：渲染过程中读盘、解码，缓存全清可能导致重复抖动【代码确认】

位置：`src/ui.rs:1607` 附近的 Block::Image 分支。

图片首次渲染直接读取原文件、完整解码并生成 PNG。images 到 48 项时 clear 全部；同时渲染的素材超过容量时，旧图会不断被淘汰再解码。PreparedAttachment 已计算 preview，attach_prepared 只用它判断图片类型，未复用到展示缓存。

建议：渲染只读取缓存状态并发起有界加载；后台生成/保存缩略图，按字节预算做 LRU。性能收益应以多图滚动和首帧耗时验证。

## 结构性技术债

### A. Store 与 Runtime 的职责边界泄漏

Store 将 db/key/root/notes/groups/settings 全部公开；UI 直接操作 sync_state，sync.rs 又自行实现 install/head/acknowledge。写库、修订、内存更新和通知分别在多个位置维护。

`persist`、`resolve_conflict`、同步 `install` 的差异有业务原因，但应共享一个事务内的对象写入原语，并明确何时创建 outbox、何时更新 head。不要用一个参数过多的万能方法合并所有语义。

建议先收口提交入口，返回持久化后的 Note 和变更事件；逐步将 db 改为受控访问。无需一开始堆叠 Repository/Service trait。

### B. 多份文档/选区状态增加同步成本

编辑器视图维护 EditorState.document、source、projection；选区同时有 state.selection 与 selection/reversed，composition 同时有 state.composition 与 marked。projection 和 source 可以是合理缓存，但目前需要人工维持一致，sync_external 的问题就是这种协议遗漏。

建议以 EditorState 为唯一可变编辑状态；投影和 Markdown 按文档版本缓存，视图不长期独立维护可写选区。让宿主消费结构化变更/快照，Markdown 逐步降为导入导出及协议兼容格式。

### C. media_archive 把本地撤销保留变成持久化、同步保留

`model.rs` 会把移除的素材保存在 archive；`sync.rs:158` 的 assets 同时收集 blocks 和 archive。因此删除节点后，附件依然上传、占用配额、保有服务端引用，不会进入 GC；media_depths 也没有对应清理。

这是撤销需求的合理起点，但缺少生命周期。应区分活动素材、会话撤销素材、历史修订引用。先明确历史/恢复保留策略，再实现可达性 GC；不能直接删除 archive 或附件文件。

### D. 历史、outbox、同步缓存缺少保留策略

每次自动保存写一份完整 Note 到 objects/revisions，outbox 已确认行继续保留；prepare 实际通过 objects 与 sync_heads 差异决定上传，并不消费 outbox 队列。outbox 目前更多是审计状态，名称容易误导。

服务端 receipts 也永久积累且不计入 used 配额。保留 receipts 保证重试幂等，不能随意清空，但长期运行需要明确容量和幂等窗口设计。

建议先增加体积统计和 no-op 保存抑制，再设计历史压缩/快照、确认状态归档及 receipts 策略。保留至少一个完整离线重试周期的语义保证。

### E. UI 驱动全局后台调度

每个 View（包括内嵌卡片）创建 80ms tick，tick 都调用共享 Runtime::drain_jobs；后者扫描待下载图片并准备同步。工作量随视图数增加，调度生命周期与窗口存活耦合。

建议由应用级单一调度器消费 job、推进同步和重试；视图订阅 NoteId 级变更。保持 SQLite 单一写入者是合理的，不必为拆分而引入共享连接锁。

### F. 性能上限尚未被结构保证

Store 启动加载所有正文和删除记录；同步 apply 每次重载所有对象；transfer 收集完所有分页才返回 Cycle；EditorState 每次编辑 clone 整份 Document，并最多保留 100 份全文快照。选区移动也会重建全文来验证 UTF-8。

小型便签可以接受；大量笔记、长正文、首次大同步会出现内存和主线程耗时上升。优先做定量基线，再考虑按对象更新缓存、分页列表、有界同步批次、合并连续输入历史、增量投影。当前无需直接换 rope 或 CRDT。

### G. 局部重构与命名欠账

`seal_local` 已只序列化 JSON，却仍接收未使用的 key；`src/rich_editor.rs` 只是兼容 re-export；口令相关 API 使用 `password`，需要先确认是否与当前依赖版本/定制工具链关联再统一命名。以上属于可读性问题，优先级低于状态一致性。

## 防御逻辑评估

以下防御应保留：AEAD 对 header 的绑定、对象/附件 ID 校验、响应与图片解码上限、服务端 BEGIN IMMEDIATE 与配额原子检查、不可变 revision/asset、409 分类、精确密文重试缓存、迁移前备份和可重入恢复。它们分别覆盖不可信输入、并发竞争、随机 nonce 和跨文件迁移失败，不能仅因重复检查就删除。

尤其 transfer 和 apply 各验证一次密文：目前 apply 为公开入口，第二次验证仍有边界价值；只有引入不能由外部伪造的 ValidatedPacket 类型后，才适合消除重复解密。

真正应收敛的是补偿状态：全局 dirty 屏障、generation 轮询、人工维护 observed_revision、media_archive 永久保留、手工回滚附件写入。它们不是单独“写得谨慎”的问题，而是领域提交与会话状态没有统一抽象后的连锁复杂度。

## 推荐推进顺序

1. 修复清空便签的一致性，明确空稿生命周期；增加跨重启/同步/继续输入测试。
2. 引入会话 base_revision 和统一提交；覆盖中心与独立窗口交错保存、IME 期间外部更新。
3. 统一后台媒体结果的目标查找、任务代次、无变化不提交。
4. 消除文字块随机 ID 对语义比较的影响；统一稳定内容比较。
5. 拆分 ui.rs 的应用调度、编辑会话和媒体缓存；将图片处理移出渲染。
6. 明确历史、归档附件、outbox/receipts 生命周期，再做 GC 和性能优化。

目标结构：View → EditSession（文档、base revision、composition、pending 更新）→ 应用命令 → Store 事务提交；SyncCoordinator/MediaJobs 也通过应用命令更新，所有视图消费相同对象变更。
